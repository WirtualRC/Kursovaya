## 2. НАЗНАЧЕНИЕ И ЦЕЛИ СОЗДАНИЯ СИСТЕМЫ

### 2.1. Назначение системы

Система предназначена для организации онлайн-игры в шахматы между двумя удалёнными пользователями с синхронизацией состояния партии в реальном времени, а также для хранения и предоставления пользователям истории сыгранных партий, статистики и рейтинга.

Система включает следующие возможности:

- регистрация и авторизация пользователей;
- подбор соперника из очереди ожидающих игроков (матчмейкинг);
- проведение партии с валидацией ходов по правилам шахмат и контролем времени;
- наблюдение за идущей партией в режиме зрителя;
- обработка разрывов соединения и повторное подключение к партии;
- фиксация результатов партий и пересчёт рейтинга игроков;
- просмотр профиля, истории партий (с возможностью воспроизведения хода партии) и таблицы рейтинга;
- создание и проведение турниров по круговой системе: регистрация участников, автоматическая жеребьёвка туров, запуск партий по расписанию, ведение турнирной таблицы.

Система рассчитана на использование следующими группами пользователей: игроками (зарегистрированными пользователями), организаторами турниров (любой зарегистрированный пользователь, создавший турнир) и администратором, осуществляющим управление учётными записями.

### 2.2. Цели создания системы

Целями создания системы являются:

- обеспечение возможности находить соперника и проводить шахматную партию без заметных задержек и рассинхронизации состояния игры между участниками;
- обеспечение корректного и эффективного хранения информации о пользователях, партиях, ходах и рейтинге в реляционной базе данных;
- предоставление пользователям возможности самостоятельно организовывать и проводить турниры по круговой системе с автоматическим формированием расписания и подсчётом результатов;
- ведение учёта результатов партий, турниров и рейтинга игроков собственными средствами, без привлечения сторонних сервисов.

## 3. ХАРАКТЕРИСТИКА ОБЪЕКТА АВТОМАТИЗАЦИИ

Объектом автоматизации является процесс организации и проведения шахматной партии между удалёнными пользователями, включающий формирование, передачу и обработку сетевых сообщений (в формате JSON) с информацией о ходах, состоянии шахматной доски, статусе партии и действиях пользователей через постоянное клиент-серверное соединение, дополненное набором REST-запросов для операций, не требующих работы в реальном времени. Процесс включает:

- регистрацию и авторизацию пользователя;
- постановку игрока в очередь ожидания и подбор ему соперника с близким рейтингом;
- создание партии и назначение сторон (белые/чёрные);
- передачу хода от игрока на сервер, проверку его допустимости по правилам шахмат и рассылку обновлённого состояния доски обоим участникам и наблюдателям;
- контроль времени на партию по шахматным часам каждого игрока;
- обработку особых действий игроков: сдача, предложение ничьей, принятие/отклонение ничьей;
- обработку обрывов соединения: ожидание повторного подключения, фиксация технического поражения по истечении тайм-аута;
- определение результата партии (мат, пат, ничья, сдача, истечение времени, техническое поражение), запись результата в базу данных и пересчёт рейтингов участников;
- создание турнира организатором с указанием названия, времени начала, режима контроля времени и ограничений по числу участников;
- регистрация игроков на турнир и отмена регистрации до его начала;
- формирование расписания турнира по круговой системе (каждый участник играет с каждым один раз) и разбиение его на туры;
- автоматическое создание партий очередного тура и оповещение участников о начале тура;
- учёт результатов турнирных партий (1 очко за победу, 0,5 за ничью, 0 за поражение, включая поражение за неявку), формирование турнирной таблицы и определение мест участников.

Объект автоматизации охватывает деятельность следующих участников:

- **игроков**, проводящих партии и просматривающих свою статистику;
- **организаторов турниров** (любой зарегистрированный пользователь), создающих турниры и управляющих ими до начала;
- **наблюдателей** (любой авторизованный пользователь, смотрящий чужую партию, не участвуя в ней);
- **администратора**, управляющего учётными записями пользователей.

## 4. ТРЕБОВАНИЯ К СИСТЕМЕ

### 4.1. Требования к системе в целом

#### 4.1.1. Требования к архитектуре системы

1. Система реализуется по клиент-серверной архитектуре. Серверная часть (REST API, WebSocket-сервер, игровая логика) разворачивается как единое приложение; клиентская часть реализуется в виде одностраничного веб-приложения (SPA).
2. Для игрового обмена в реальном времени используется протокол WebSocket (RFC 6455); для остальных операций (регистрация, авторизация, профиль, история партий, рейтинг) используется HTTP/REST. Формат обмена данными — JSON.
3. Внутри серверной части применяется модульный принцип построения: логическое разделение на независимые модули (авторизация, матчмейкинг, игровая логика и валидация ходов, управление партиями и соединениями, рейтинг, турниры, доступ к данным), взаимодействующие через внутренние программные интерфейсы.
4. Серверная часть реализуется на языке Python 3.x с использованием фреймворка Flask и расширения Flask-SocketIO (или аналога для WebSocket); клиентская часть — на React; для хранения данных используется реляционная СУБД PostgreSQL.
5. Состояние партии является авторитетным на сервере: клиент отправляет только намерение хода, а решение о допустимости хода и обновление состояния принимает сервер.
6. Архитектура обеспечивает модифицируемость (возможность доработки отдельных модулей без изменения структуры системы в целом) и функциональную расширяемость (например, добавление новых режимов контроля времени).

#### 4.1.2. Требования к надёжности

1. Система должна сохранять работоспособность при кратковременных обрывах сетевого соединения клиентов: при разрыве партия не должна теряться, а клиент должен иметь возможность вернуться в неё и получить актуальное состояние.
2. Должна обеспечиваться целостность данных о пользователях, партиях, ходах и рейтинге, а также ссылочная целостность между ними.
3. Запись результата завершённой партии и пересчёт рейтингов обоих участников должны выполняться атомарно (в одной транзакции).
4. Каждый ход должен сохраняться с указанием порядкового номера и времени, что позволяет полностью восстановить партию.
5. Сетевой обмен должен логироваться (время хода, задержки, ошибки соединения).
6. Должна обеспечиваться целостность турнирных данных: расписание турнира формируется один раз при его запуске, каждая пара тура ссылается на двух участников турнира, результат пары согласован с результатом связанной партии. Внесение результата пары и обновление турнирной таблицы выполняются атомарно.

#### 4.1.3. Требования к безопасности

1. Доступ к игровым функциям и данным профиля осуществляется только после аутентификации пользователя. Пароли хранятся в базе данных только в виде криптографических хэшей с использованием соли.
2. WebSocket-соединение устанавливается только для аутентифицированных пользователей (по токену, полученному при авторизации).
3. Система должна разграничивать права доступа: игрок может совершать ходы только в своих партиях и только в свою очередь; наблюдатель имеет доступ только на чтение; организатор турнира может изменять или отменять только созданный им турнир и только до его начала; администратор имеет доступ к управлению учётными записями и может отменить любой турнир.
4. Все входящие данные (в том числе сообщения WebSocket) проверяются на стороне сервера; некорректные сообщения отклоняются без влияния на состояние партии.
5. Передача данных между браузером пользователя и системой должна осуществляться по защищённому соединению (HTTPS/WSS).

#### 4.1.4. Требования к эргономике и пользовательскому интерфейсу

1. Интерфейс должен быть интуитивно понятным. Шахматная доска должна поддерживать ход фигурой перетаскиванием (drag-and-drop) с подсветкой допустимых полей.
2. На экране партии должны отображаться: индикатор статуса соединения («подключено» / «соединение потеряно» / «ожидание соперника»), шахматные часы обоих игроков, история ходов в алгебраической нотации, статус партии и результат.
3. Основные действия (поиск соперника, ход, сдача, предложение ничьей) должны выполняться за минимальное число действий пользователя.
4. Для наблюдателей предусматривается отдельный режим отображения партии без возможности совершать ходы.
5. Интерфейс должен корректно отображаться на экранах стандартных размеров настольных компьютеров и ноутбуков.

### 4.2. Требования к функциям, выполняемым системой

#### 4.2.1. Функции серверной части

1. Приём и установление WebSocket-соединений от клиентов, проверка пользователя при подключении, поддержание соединения (пинг/понг).
2. Матчмейкинг — подбор соперника из очереди ожидающих игроков (с учётом рейтинга и выбранного режима контроля времени), создание партии и назначение цветов фигур.
3. Валидация ходов по правилам шахмат (включая рокировку, взятие на проходе, превращение пешки, шах, мат, пат) и обновление состояния партии на сервере.
4. Рассылка обновлённого состояния доски обоим участникам партии и всем наблюдателям в реальном времени.
5. Контроль времени на партию (шахматные часы) на стороне сервера; фиксация поражения по времени.
6. Обработка действий игроков: сдача, предложение ничьей, ответ на предложение ничьей.
7. Обработка обрывов соединения: ожидание повторного подключения в течение заданного тайм-аута, восстановление состояния партии при реконнекте, фиксация технического поражения при превышении тайм-аута.
8. Поддержка режима наблюдателя: подключение к идущей партии и получение её текущего состояния и последующих обновлений.
9. Определение результата партии, запись её в базу данных и пересчёт рейтинга обоих участников.
10. Обработка REST-запросов: регистрация и авторизация пользователя, получение профиля, истории партий, данных отдельной партии (список ходов), таблицы рейтинга, списка активных партий, списка турниров, данных турнира, турнирной таблицы и расписания туров.
11. Ведение журнала сетевого обмена.
12. Обработка операций с турнирами: создание, изменение и отмена турнира организатором, регистрация и отмена регистрации участников с проверкой ограничений (срок регистрации, максимальное число участников).
13. Автоматический запуск турнира в назначенное время: при наличии не менее минимально допустимого числа участников (не менее 4) — формирование расписания по круговой системе (с учётом нечётного числа участников и пропуска тура), иначе — автоматическая отмена турнира.
14. Автоматический запуск туров: создание партий для пар очередного тура, оповещение участников по WebSocket, ожидание подключения игроков; при неявке игрока в течение заданного тайм-аута засчитывается поражение за неявку.
15. Завершение пар и туров при окончании связанных партий, начисление очков, пересчёт турнирной таблицы и определение итоговых мест (при равенстве очков — по коэффициенту Бергера); завершение турнира после окончания последнего тура.

#### 4.2.2. Функции клиентской части (игрок)

1. Регистрация и авторизация в системе.
2. Установление и поддержание WebSocket-соединения с сервером, автоматическая попытка повторного подключения при обрыве.
3. Постановка в очередь поиска соперника и отмена поиска.
4. Отображение шахматной доски, обработка действий пользователя (выбор и перемещение фигуры, выбор фигуры при превращении пешки).
5. Отображение статуса игры, статуса соединения, шахматных часов и истории ходов.
6. Сдача партии, предложение и принятие/отклонение ничьей.
7. Просмотр профиля, статистики (число партий, побед, поражений, ничьих), рейтинга и истории сыгранных партий через REST API.
8. Просмотр завершённой партии с пошаговым воспроизведением ходов.
9. Просмотр таблицы рейтинга игроков.
10. Просмотр списка турниров (предстоящие, идущие, завершённые), страницы турнира с составом участников, расписанием туров и турнирной таблицей.
11. Регистрация на турнир и отмена регистрации.
12. Получение уведомления о начале тура и переход к турнирной партии; отображение того, что партия является частью турнира.
13. Просмотр истории турнирного участия в профиле (занятые места, набранные очки).

#### 4.2.3. Функции наблюдателя

- просмотр списка идущих партий;
- подключение к выбранной партии и наблюдение за ходом игры в реальном времени (без возможности совершать ходы).

#### 4.2.4. Функции организатора турнира

Организатором турнира может стать любой зарегистрированный пользователь. Организатору доступны:

- создание турнира с указанием названия, описания, даты и времени начала, режима контроля времени, минимального и максимального числа участников (в пределах от 4 до 16);
- изменение параметров турнира и его отмена до начала турнира;
- просмотр списка зарегистрированных участников;
- просмотр хода и результатов собственного турнира.

После начала турнира организатор не может вмешиваться в расписание и результаты партий.

#### 4.2.5. Функции администратора

- управление учётными записями пользователей (просмотр списка, блокировка и разблокировка);
- отмена любого турнира, нарушающего правила платформы;
- просмотр общей статистики системы (количество пользователей, партий, турниров).

### 4.3. Требования к видам обеспечения

#### 4.3.1. Требования к программному обеспечению

1. Серверная часть: Python 3.x, Flask, Flask-SocketIO (или аналог для WebSocket); для проверки правил шахмат допускается использование специализированной библиотеки.
2. Клиентская часть: React; доступна из современных браузеров без установки дополнительного программного обеспечения.
3. СУБД: PostgreSQL.
4. Протоколы: WebSocket (RFC 6455) для игрового обмена, HTTP/REST — для остальных операций.

#### 4.3.2. Требования к информационному обеспечению

1. Структура данных проектируется на основе концептуальной, логической и физической моделей данных. Предварительный состав сущностей: пользователь, партия, ход, запись об изменении рейтинга, турнир, участие в турнире, тур, пара. Состав и атрибуты сущностей уточняются в ходе проектирования. При проектировании должны быть учтены следующие связи:
   - пользователь — партия (один ко многим, дважды): партия ссылается на игрока белыми и игрока чёрными фигурами;
   - партия — ход (один ко многим);
   - пользователь — запись об изменении рейтинга и партия — запись об изменении рейтинга (один ко многим); запись хранит рейтинг игрока до и после партии;
   - контроль времени задаётся атомарными числовыми атрибутами «начальное время» и «прибавка за ход» (в секундах) в сущностях «партия» и «турнир»; формат турнира задаётся атрибутом с ограничением допустимых значений (реализуется круговая система);
   - пользователь (организатор) — турнир (один ко многим);
   - пользователь — турнир (многие ко многим) через сущность «участие в турнире», в которой хранятся дата регистрации, набранные очки и итоговое место;
   - турнир — тур (один ко многим);
   - тур — пара (один ко многим); каждая пара ссылается на два участия в турнире (участник с белыми и участник с чёрными фигурами) и хранит результат;
   - пара — партия (один к одному, необязательная): партия создаётся для пары, но при неявке игрока или пропуске тура пара может не иметь партии. Партия вне турнира не связана с парой.
2. Схема базы данных должна быть приведена к третьей нормальной форме (3НФ), если иное не обосновано в записке.
3. Для таблиц должны быть определены первичные и внешние ключи, ограничения целостности (NOT NULL, UNIQUE, CHECK) и индексы, обеспечивающие эффективную выборку (история партий пользователя, таблица рейтинга, ходы партии, список турниров по статусу и дате, расписание и таблица турнира).
   Должны быть обеспечены ограничения: пользователь может зарегистрироваться на турнир только один раз; пара не может включать одного и того же участника дважды; в одном туре участник входит не более чем в одну пару.
4. Состояние доски передаётся в формате FEN (или аналогичном); ход — в формате координат (например, «e2-e4») с последующей записью в алгебраической нотации.
5. Выходные данные: актуальное состояние доски в формате JSON, результат партии, обновлённый рейтинг игрока, лог-файлы сетевого обмена.

#### 4.3.3. Требования к техническому обеспечению

Серверное оборудование должно обеспечивать одновременную работу не менее 50 активных партий и хранение накапливаемых данных с возможностью последующего наращивания ресурсов. Клиентское устройство — компьютер с современным браузером и доступом к сети Интернет.

#### 4.3.4. Требования к лингвистическому обеспечению

1. Язык пользовательского интерфейса — русский (допускается добавление английского).
2. Система должна обеспечивать корректный ввод, хранение и обработку текстовых данных в кодировке UTF-8.

### 4.4. Требования к производительности

1. Задержка между отправкой хода одним игроком и получением обновлённого состояния доски вторым игроком в штатных условиях не должна превышать 300 мс.
2. Время подбора соперника при наличии в очереди подходящего игрока не должно превышать 3 секунд.
3. Время ответа REST API на запросы профиля, истории и рейтинга не должно превышать 1 секунды.

## 5. СОСТАВ И СОДЕРЖАНИЕ РАБОТ ПО СОЗДАНИЮ СИСТЕМЫ

1. **Анализ предметной области и проектирование модели данных.**
   Определение состава и структуры сущностей (пользователи, партии, ходы, изменения рейтинга, турниры, участия в турнирах, туры, пары), построение концептуальной и логической моделей (ER-диаграмма), проектирование физической модели и реализация схемы в СУБД PostgreSQL.

2. **Исследование технологий сетевого обмена.**
   Изучение принципов работы протокола WebSocket, обоснование его выбора в сравнении с альтернативными способами организации обмена (HTTP-опрос, long polling); выбор формата обмена данными (JSON). Демонстрация макета обмена ходами между двумя клиентами.

3. **Проектирование архитектуры системы.**
   Разработка схемы клиент-серверного взаимодействия, включая матчмейкинг, обработку ходов, режим наблюдателя и обработку разрывов соединения; определение модульной структуры приложения; проектирование REST API и форматов WebSocket-сообщений; прототипирование интерфейса.

4. **Программная реализация серверной части.**
   Реализация WebSocket-сервера и REST API, авторизации, матчмейкинга, валидации ходов, шахматных часов, обработки обрывов соединения и реконнекта, записи результатов и пересчёта рейтинга; реализация модуля турниров (регистрация участников, формирование расписания по круговой системе, автоматический запуск туров и партий, обработка неявок, подсчёт очков и мест).

5. **Разработка пользовательского веб-интерфейса.**
   Реализация экранов авторизации, поиска соперника, игровой доски, профиля, истории партий, таблицы рейтинга и режима наблюдателя; экранов списка турниров, создания турнира, страницы турнира (участники, расписание, турнирная таблица).

6. **Тестирование.**
   Проверка корректности шахматных правил, сетевого взаимодействия (установление и разрыв соединения, синхронизация состояния между клиентами, реконнект, тайм-ауты), авторизации и работы с базой данных, а также корректности формирования расписания кругового турнира (для чётного и нечётного числа участников) и подсчёта очков; отладка приложения.

7. **Подготовка документации.**
   Написание расчётно-пояснительной записки, включающей руководство пользователя и руководство программиста; подготовка доклада и демонстрации.

## 6. ПОРЯДОК КОНТРОЛЯ И ПРИЁМКИ СИСТЕМЫ

1. Контроль выполнения требований осуществляется на каждом из этапов, указанных в разделе 5 настоящего технического задания.
2. Проверке подлежат основные функциональные возможности системы:
   - регистрация и авторизация пользователей;
   - установление и разрыв WebSocket-соединения, корректное отображение статуса соединения;
   - подбор соперника и создание партии;
   - синхронизация состояния партии между двумя клиентами и наблюдателем;
   - отклонение недопустимых ходов, корректная обработка мата, пата, рокировки, взятия на проходе и превращения пешки;
   - работа шахматных часов и фиксация поражения по времени;
   - обработка обрыва соединения: реконнект в пределах тайм-аута и техническое поражение при его превышении;
   - запись результата партии и корректный пересчёт рейтинга;
   - получение истории партий, профиля и таблицы рейтинга через REST API;
   - создание турнира любым пользователем, регистрация и отмена регистрации участников, соблюдение ограничений по числу участников;
   - автоматический запуск турнира в назначенное время или его отмена при недостатке участников;
   - корректность расписания круговой системы: каждый участник играет с каждым ровно один раз, при нечётном числе участников каждый пропускает ровно один тур;
   - автоматическое создание партий очередного тура и поражение за неявку по истечении тайм-аута;
   - корректный подсчёт очков, формирование турнирной таблицы и определение итоговых мест.
3. Работоспособность реализованных функций подтверждается результатами функционального тестирования. При добавлении новой функциональности ранее пройденные тесты соединения и авторизации должны сохранять работоспособность.
4. Сдача-приёмка работ производится поэтапно в соответствии с учебным планом; основанием для приёмки очередного этапа служит отчёт исполнителя с сопроводительной документацией согласно разделу 8.
5. Итоговая проверка системы осуществляется в рамках защиты курсовой работы комиссией кафедры ИУК5 КФ МГТУ им. Н.Э. Баумана.
